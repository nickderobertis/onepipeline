# Modular crate layout: dependency design and conservative replay

This is a design, not a source refactor. It preserves the current command behavior, public `onepipeline` API, tests, platforms, release cadence and coverage floor. The proposed DAG is mechanically acyclic, but the conservative replay does **not** establish a useful gate speedup or the 30-minute goal. Do not schedule the whole extraction on the premise that it does.

The executable inputs are `scripts/modularization/layout.json` and the current source. Run:

```sh
node scripts/modularization/graph.mjs
node scripts/modularization/replay.mjs scripts/modularization/layout.json target/modularization.json
node scripts/modularization/render.mjs
just nx run onepipeline-npm:test
```

`layout.json` is research data, schema 1. It assigns each Rust file exactly once, names dependencies and the disposition of every discovered source edge, and maps test modules to suites. Empty `files` on a command crate means its adapter must be extracted from today's `driver::dispatch`/`verbs`, not that an implementation already exists. `assets` assigns the two non-Rust inputs under `src/`. `auxiliarySuites` inventories the other journey projects without pretending their timing is present in the e2e profile.

The profile report in that revision supplies the all-module timing table: local Linux at 7a017fa, CI Linux/macOS/Windows at dd2e5d6 (run 39098714538). Those are historical measurements, not timings of this design or this tree. The replay reads the report's rounded module seconds directly. It stops at the earlier-records details block so the two record sets cannot overwrite one another. Missing platform records remain missing; the Windows result is an observed-record subset, not a prediction of its unobserved tests. Local totals differ slightly from the raw-record figures because the table rounds each module to whole seconds.

The preceding CI spike is the branch `origin/nick/ci-time-budgets-wave1/spike-onepipeline-ci`; its checked-in `spike/onepipeline-ci/out/report-answers.json`, analysis scripts and fixture data are the upstream measurement harness. Its local attempts did not produce a valid cold full-gate measurement; this design does not manufacture one from those attempts.

The module graph here is a **syntactic dependency inventory**, including `cfg(test)` and all platform branches. It scans qualified `crate::`/`onepipeline::` paths and grouped crate imports, strips literals/comments, and folds directory children into their root module. Sites in the edge appendix permit inspection. It is not rustc name resolution: macro-generated edges and glob re-exports require review during extraction. `lib` and `main` are composition roots. The historical report's 68-of-73 cycle and this snapshot's cycle have different source revisions and extraction definitions; neither count replaces the other. In particular, today `error` reaches channel's structured refusal, and `sys` reaches the ordering hook; treating either as an independent leaf would be wrong.

## Boundary rules

The unit of ownership is a concept or one command. There is no `core`, `common`, `utils` or all-purpose implementation crate. `scheduler` is the reconcile loop; `run-control` is process ownership, handover, adoption and teardown; `publication` is lifecycle publication and settlement; `task-store` is the taskgraph read/write projection boundary; `run-record` is durable paths and records. These are distinct contracts even where today's modules mix their implementations.

The source-owner table assigns every module's main body once. The edge table also specifies the pieces that must move out of that body. Ownership is not permission to copy types or change wire formats. A shared DTO moves to its lowest concept owner and is re-exported at its original path. For example, moving channel's structured refusal into diagnostics must preserve the identity of `Error::Rejected(channel::Refusal)`, not translate it into an incompatible replacement. CLI argument DTOs must stop depending on renderers. Event registry construction must accept producer registrations rather than import every producer implementation.

An inverted edge is a real implementation requirement, not an edge the measurement silently deletes. The depending concept owns the interface; the facade installs the production adapter. Channel's `EnvelopeValidator` takes an envelope plus immutable run snapshot and returns acceptance/refusal. Task-store's `ProjectionSource` provides the revisioned projection. Publication's `SettlementSink` writes a settlement through the owner of the run journal. Agent execution's dispatch/completion interfaces exchange node, launch and result DTOs. Journal accepts its registry/fold callback. None asks a sibling to import onepipeline or moves host policy into this repository.

The facade re-exports all existing contract modules and preserves `run`, `VERSION`, type identity, serialized fields, error variants and exit codes. Its binary performs parse → command entry point → render → exit. `tests/contract.rs` and `tests/parity.rs` remain full-facade proofs. Internal crate visibility must not become new promises in the facade documentation.

**Recommended packaging:** publish the implementation crates in lockstep behind the existing public facade. The manager approved making that recommendation in this design (reply 155, correlation c-0bc5ddb3d6b3bdf79eb23d543071383e). The user reviews the additional packages through this document; this task changes no release target or automation. A future implementation must add the approved package set to the existing single version driver's process before the first extracted dependency ships.

The alternative is to retain the published library and shipped binary as a monolithic Cargo package, with workspace-only command adapters/test runners calling it. That preserves the current registry surface and public type identities, but shared implementation edits still rebuild that monolith and invalidate its command consumers. It cannot provide the requested concept-level compilation isolation; its conservative selection remains close to the historical four-crate proposal. Including source files into multiple unpublished crates also does not make those crates publishable dependencies of the facade. The lockstep recommendation pays release coordination cost to obtain real Cargo compilation units.

## Test execution and selection

A command suite must compile a subprocess runner composed from the same CLI schema and production command entry points as the shipped binary. It must use real record writers, real channel validation, real scheduling and the repository's existing subprocess doubles. A runner assembled from only the needed commands is not a substitute implementation. Detached start/adopt runners also include the hidden `drive-run` adapter, declared as a dependency of those command crates, because their retained executable re-enters that verb. A full-dispatch/facade suite still drives the shipped binary, catching routing and packaging failures. If every suite continues to request the full shipped binary as a build dependency, there is no command-level compile selection: declaring narrower Nx dependencies in that situation would be incorrect.

The module suites in the mapping retain conservative command unions from the profile's nine areas and add command families named literally in each module or its borrowed helpers. This includes all template subcommands for template journeys, rather than inferring their roots from an area name. The `onepipeline-modularization` Nx project owns the historical replay and real-Nx tests, separately from launcher tests. Completeness is checked against modules declared in `tests/e2e/main.rs` that contain test functions; helper-only `budget_result` and `recorded_support` remain transitive suite inputs. The updater derives subcommand families from the `Command` and nested command enums in `src/cli.rs`; the freshness test checks both file inputs and these command roots. Replay derives shared build inputs from Nx’s `rustBuild` named input through the existing recursive parser, with schemas and source guidance retained as conservative shared inputs. Each includes start, observation and teardown where those fixtures can execute them. This is why apparently read-only assertions still reach the scheduler. The measurement does not assume they can be changed to recorded fixtures without cost or coverage analysis. The per-module suite is an attribution unit; it does not create a CI job or a shard. All selected suites execute in the same platform job with the same test inventory.

Every test module in the suite appendix needs import/runner-path changes when it crosses a crate boundary. Borrowed helper functions currently imported from another test module must move into the test-support library; importing that module wholesale into two binaries would run its tests twice. Keep each test in exactly its listed owner, with its existing assertions, failures, platform guards and test names. `tests/e2e/harness.rs` needs its executable lookup/build command to target the suite runner. Profiling journeys that spawn the test binary itself retain that behavior. Contract, parity, release/install and packaging journeys retain the full facade/binary. No test is removed, weakened, sampled or moved off a platform in this design.

Shared Cargo manifest/lock/toolchain/config inputs invalidate every suite. Testfakes invalidate every suite using them. A historical `driver.rs` edit is attributed conservatively to run-control, even if a future function-level extraction could put that change in a smaller adapter. Test paths retain the profile mapping's borrowed-module and runtime-fixture inputs. Future measurements may narrow them only after helper extraction proves that a file is no longer compiled or read by a suite.

## Savings and compile cost

The previously stale `e2e-store` input set is corrected here: it now includes borrowed `review_reply` and its transitive inputs. The existing replay regression originally refused the baseline for omitting that file; it passes after correction. `suite-inputs.mjs` discovers those inputs from current test source and updates either mapping. The generated tables have a freshness check, and the tests verify borrowed-file/runtime-input coverage rather than just module ownership.

The generated results below replay exactly the same 144 first-parent non-release PRs, 2026-09-15 through 2026-10-15 inclusive. Suite-count percentages have an 88-suite denominator and should not be read as wall-clock percentages. Today's profile result is 2.1% of suite runs and test-seconds skipped. The originally reported four-crate result was 4.7% of suite runs; after correcting borrowed-module inputs it fell to 4.5%, and the profile mapping at b0ce59c reports 4.4% (4.0% of seconds). The comparison must retain those corrections.

This design's modest improvement over today's graph is an aggregate, not a bound on the slowest PR. The profile found 85/144 changes to shared build inputs, so those PRs still run every suite. Even perfect separation cannot eliminate their full test cost. The manager was asked about the 30-minute constraint with this evidence (c-81b072e384e8a93692575f24690aaaf5) and about the negative conservative replay (c-ebd0a0f4ebc6ab5ff08ed9f2a33e2ffb). No coverage tradeoff is assumed.

There is **no measured compile-time saving for this unimplemented layout**. The profile's f6a526e prototype measured Linux cold whole-job CPU 574 → 795 seconds for nine suites, incremental source edit 193 → 264 seconds, and one-suite cold CPU 405 → 286–331 seconds. It measured 326 → 312 seconds median cold wall at `-j4`, explicitly within noise; local source-edit wall 51 → 74 seconds was also load-sensitive. That prototype is the four-crate split, not this design. Mac and Windows compile effects were not measured.

A transparent stress estimate, not a benchmark: if the prototype's extra per-suite whole-job CPU cost stayed constant, 88 suites would cost `574 + (795-574)/8 * 87 = 2,977` CPU seconds on that Linux host, and an incremental all-source rebuild `193 + (264-193)/8 * 87 = 965` CPU seconds. Narrow command runners may lower that cost; extra crate interfaces and links may raise it. This estimate argues against implementing 88 separately linked binaries without first measuring command-group runners. It supplies no reliable macOS or Windows compile ratio. Their additional links are real work; a claimed numeric speedup there would be unsupported.

For the local gate, skipped test-seconds below are a workload estimate only. At most they save those seconds divided by effective test concurrency, while the critical-path test, build dependency ordering, coverage merge and judged lint remain. With about 4% fewer test-seconds and the above extra-link risk, this layout does not establish a faster local gate. An unchanged-file warm Nx hit already avoids execution; these estimates concern changed-file cache misses. No full gate was rerun for this research task.

## Migration discipline

The generated order extracts dependency leaves first. For each step: first implement its listed interfaces/DTO moves inside today's crate with forwarding modules; then move that concept into its crate; re-export the exact old API paths; keep the command adapters forwarding until their turn. Keep the shipped dispatcher and every existing test passing throughout. Run the affected concept's tests plus the unchanged contract/parity proofs for a public type move; keep publication/channel/recovery journeys on the real adapters. No migration step may update the frozen contract to make extraction easier.

The order below reports the conservative skip fraction after each extraction. Until a suite's runner and all its dependencies have been extracted it still depends on the residual crate. Residual depends on every extracted crate, so a prematurely narrowed suite cannot inflate intermediate savings. Extracting leaves alone therefore buys little or nothing. Adapter-only command extractions can land independently once their concept dependencies exist, preserving stdout, stderr, exit status and environment handling by forwarding to the same implementation.

These are structural step proposals, conditional on user approval of the packaging recommendation and on proving each seam by implementation. The acyclic mapping is not evidence that dozens of interfaces can be mechanically generated or that any particular extraction already compiles. The source remains untouched in this task.
