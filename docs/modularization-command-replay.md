# Command-suite replay and the remaining design decision

This is the conservative unsplit-test baseline committed at bffb01b3 (6.61% suite skipping), retained for comparison. [The target layout](modularization-target-layout.md) supersedes its architecture and test-boundary proposal. [The source-graph design](modularization-design.md) remains the exhaustive cycle inventory. Earlier unanswered manager questions were resolved by ruling 205.

The machine-readable schema-1 catalog in `scripts/modularization/command-tests.json` maps every current `tests/e2e/main.rs` test function exactly once, with its command roots and why it moves. A command runner links its own command crate and the shared crates that command uses. It does not request the published full binary. The explicitly enumerated `cross-command` exception suite uses the facade and shipped dispatcher, preserving original causal journeys and assertions. No test, platform, assertion or failure path is removed, sampled or weakened. Existing tests outside the e2e binary remain mapped by `layout.json`'s `auxiliarySuites`; they have no profile weights here.

The catalog is a **candidate conservative attribution**, not a compiler proof of future runner boundaries. Inventory generation recognizes literal command argument arrays and follows named local helpers. Borrowed helpers and dynamic argument construction need manual review during extraction. The catalog's breadth must not be mistaken for an irreducible floor: the graph still has wide `run-views`, `run-record` and CLI-schema dependencies, and the source attribution keeps a whole historical module with its concept owner. The original broad union of nine profile areas is no longer added to every test; tests without a statically discovered command retain their prior conservative module union. Each test module must have its helpers moved into independently linked support modules before it can leave the current binary. `harness.rs` must dispatch through the selected runner and move process cleanup into the common process-ownership support; tests of the stop command retain their actual stop invocation. Imports of facade types become imports of their concept owner, with the facade continuing to re-export those identical types. Each catalogued test retains its assertions and name in the owner suite. Cross-command tests retain all command calls. The separate JSON enumerates every affected test, rather than asserting that a module contains only one kind of journey.

Manager ruling 205 subsequently authorized setup/consumer decomposition while retaining live causal journeys. The resulting target is in [the target layout](modularization-target-layout.md). This baseline is kept for comparison; its broad exception set is not the target.

## Reproduction and input projection

```sh
node scripts/modularization/pinned.mjs -- node scripts/modularization/graph.mjs
node scripts/modularization/pinned.mjs --write-back -- node scripts/modularization/command-replay.mjs "$ONEPIPELINE_NODE_SCRATCH_DIR/command-replay.json" --write-doc
just nx run onepipeline-modularization:check
```

The 144 PRs and source graph come from the same local first-parent history and profile report as the original design. No new benchmark is substituted for the spike. The module timing snapshots are 7a017fa (local) and dd2e5d6 (CI); the source assignment snapshot remains b0ce59cc40484264fe42adf27b89a32bd345be0e. The candidate test inventory is checked against the source files of the pinned reviewed commit (see [the source-graph report](modularization-design.md)). Module seconds are equally allocated across that module's existing tests to estimate command weights. That is deliberately labelled an estimate: a slow integration test and a fast CLI refusal will not actually take equal time. The report lists missing platform measurements in its JSON. CI platform selection uses the conservative union of cfg branches; it does not infer Windows-only savings from missing records.

Today's historical figure is 2.1% suite runs skipped. The earlier four-crate profile reported 4.7%; its corrected replay and platform test-seconds are in the original design's comparison table. These are different suite denominators: the current binary is one suite, the profile has nine areas, and this candidate counts only nonempty command runners plus the integration suite. Percentages of suite runs cannot stand in for time saved.

`Cargo.lock` is not a global selection edge in this candidate. For each crate, the script inventories external package roots referenced in its source (and test imports for runners), walks version-qualified transitive dependencies in **both** historical locks, and compares the complete reachable package records, including checksums and dependency edges. A removed, added or changed reachable record changes `resolved/<crate>/lock.json`; unrelated lock churn does not. All versions of an ambiguous unqualified dependency are conservatively included. This is a package-record projection, not Cargo feature/target resolution: cfg-only dependencies may overselect a platform. Macro-generated/relocated external imports still require review before implementing the layout. Manifest changes remain conservative and select every crate, rather than silently omitting a changed feature or requirement. Toolchain input is explicitly associated with each Rust crate and runner; the current uniform pin legitimately changes all of them. The current resolver normalizes the pin before comparison, so byte-identical and comment-only pin edits do nothing.

The eventual Nx preparation step must materialize these fingerprints **before** asking Nx for affected projects. Each projection directory is a real Nx input project with an explicit consuming-crate dependency; ordinary crate dependencies propagate it transitively to suite projects. Raw lockfiles/toolchain pins must no longer appear in shared Rust named inputs. The regression drives the public `--resolve` CLI on real lockfiles, commits projected inputs in a scratch workspace and compares script selection to real `nx show projects --affected`: command edit, transitive shared edit, relevant lock update and toolchain update. It also proves unrelated lock contents leave other runners unaffected, refuses an unresolved dependency and recovers after repair. This is a required migration prerequisite, not an enforcement change made by this design task.

## Compile and local-gate implications

There is no compiled version of this proposed layout, so compile effects remain estimates, not measurements. The original design records the spike/profile harness and Linux prototype measurements (574 → 795 cold CPU-seconds for nine runners; 193 → 264 incremental CPU-seconds). With N nonempty runners the same deliberately pessimistic linear link-cost stress model gives `574 + (795-574)/8*(N-1)` cold CPU-seconds and `193 + (264-193)/8*(N-1)` incremental CPU-seconds. Command runners should contain fewer dependencies; extra links can still dominate. Use the generated N below rather than the original document's 88-runner stress case.

Linux, macOS and Windows hosted build-phase wall baselines and the stress-estimate method are recorded in the original design's compile table. For this candidate, use `1 + (795/574 - 1)*(N-1)/8` times each platform's baseline cold build phase as the upper stress scenario, and unchanged baseline as the no-compile-saving scenario. These are extrapolations of a Linux CPU ratio to hosted wall time, not a calibrated platform forecast. A source PR selects a subset of crates and runners, so there is no honest fixed per-job compile delta until those runners exist and are built by the spike harness. No CI timeout or budget changes here.

Likewise the local gate has no new measured wall clock. Its historical full e2e run F took 10,293.5 seconds under high shared-host load. Multiplying its test phase by the local estimated seconds-skip share below is only a scenario for average work removed, not a wall-clock prediction: nextest concurrency, the unchanged deterministic tiers, compilation and the slowest selected test still govern elapsed time. This candidate's savings do not support a 30-minute promise. No sharding or coverage tradeoff is used to make that promise appear true.
